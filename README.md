# Guardly downloads

This repository publishes Guardly Linux downloads and signed update metadata. Application and connector source repositories remain separate. Corresponding source and notices accompany each published binary through immutable GitHub Release assets.

No application release is currently published. The signing authority is in `authority.json`; its public key authenticates update manifests after an independently trusted bootstrap installation. Private keys and publisher state remain with the offline operator.

The manual Pages workflow downloads only catalogued release assets, verifies their SHA-256 and length, verifies the stable manifest's detached P-256 signature, and deploys the site as one artifact. Keep at most three AppImages and a total site budget below 900 MB. Source archives stay on Releases and must fit GitHub's 2 GiB per-file limit. Never commit binary archives or private evidence here.

Before adding a release, validate its installed upgrade and rollback journey under this authority, scan the public files for secrets, and record exact binary/source hashes and source provenance. Upload assets before cataloguing them. Asset replacement requires a new release identity. Dispatch the workflow after review, then verify direct HTTPS status, absence of redirects, exact bytes and signatures at the public endpoints. A successful workflow alone does not establish consumer acceptance.

Each `Releases` entry uses `Version`, `Tag` (`v{Version}`), `SourceProvenance`, and `Assets`. Its assets are `Guardly.AppImage`, `consumer.tar.gz`, `source.tar.gz`, and `NOTICE.txt`, each with `Sha256` and `ByteLength`. Rename the exact reproducible managed installer tarball produced by `release_bundle.py` to `consumer.tar.gz` when uploading; renaming preserves bytes. The builder checks its embedded AppImage, production channel, installation receipt and required installer/notices files. Source delivery must be reviewed and bound to the same candidate through its preserved source inventory and source delivery receipt before upload. The Pages builder checks GitHub's immutable asset digest and length for the source archive without downloading its approximately 2 GB payload.

`Stable` is either null or an object with `Version`, `MetadataTag` and `Assets`. Metadata assets are `manifest.json` and `signature.der`, each with `Sha256` and `ByteLength`. Use a distinct immutable metadata release such as `metadata-v0.1.1-r0000`, then `metadata-v0.1.1-r0001` for renewal. Run `sign_release.py refresh` locally with the operator-owned key and durable state, upload the exact renewed files to the new metadata release, update only the stable metadata tag and hashes, and deploy. The versioned binary URL and immutable binary/source release remain unchanged. Keep the latest successful preparation and receipts for the next renewal.

The daily expiry workflow fails when deployed stable metadata has less than 48 hours remaining or cannot be fetched directly. Subscribe to Actions failure notifications for this repository and monitor that workflow; GitHub may delay scheduled jobs or disable schedules after repository inactivity. It holds no private key and performs no renewal. The operator reviews and signs renewal locally, then deploys it. Run the manual expiry workflow after every deployment. Empty scaffold deployments have no expiry obligation.

For a new Linux installation, download `consumer.tar.gz` from the index, check its SHA-256, extract it, and run `python3 install.py` inside `Guardly/` as the ordinary user. Requires Python 3 and working AppImage FUSE support. Authenticate the publisher independently before trusting a first download; hashes and the public key on this same site cannot by themselves establish that first trust.
